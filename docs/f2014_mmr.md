# F2014 MMR 검색 적용

## 설정
| 값 | 설정 위치 | 의미 |
|---|---|---|
| `SEARCH_TYPE = "mmr"` | `src/config.py` | 기본 검색 방식 (화면 사이드바에서 similarity로 바꿀 수 있음) |
| `TOP_K = 5` | 〃 | 외부 문서 근거 수 (특허 메타데이터 1건은 별도로 항상 포함) |
| `MMR_FETCH_K = 30` | 〃 | 유사도 상위 30개를 후보로 가져온다 |
| `MMR_LAMBDA = 0.5` | 〃 | 후보 중에서 질문 유사도와 이미 고른 청크와의 차이를 반반 반영해 k개를 고른다 |

구현: `src/rag/retriever.py`의 `search_docs()` — 두 방식 모두 `item_id` 필터로 선택한 특허의 문서만 검색한다.

## 비교 방법
`python -m src.eval.compare_search [--top-k N]`
문서를 수집해 둔 특허 3건에 대표 질문을 하나씩 주고, 같은 질문에 두 방식을 적용해 근거 목록을 비교했다.

- **서로 다른 문서 수**: 근거로 뽑힌 청크가 몇 개의 문서에서 왔는가
- **청크 간 겹침**: 뽑힌 청크끼리의 평균 코사인 유사도 (낮을수록 내용이 덜 겹친다)
- 원자료: [eval/f2014_mmr_k5.md](eval/f2014_mmr_k5.md), [eval/f2014_mmr_k10.md](eval/f2014_mmr_k10.md)

## 결과 (k = 5)
| 특허 | 문서 수 (유사도 → MMR) | 겹침 (유사도 → MMR) | 출처 구성 변화 |
|---|---|---|---|
| 지터 측정 회로 | 2 → 5 | 0.649 → 0.338 | 위키 3·청구항 2 → 위키 4·청구항 1 |
| 스캔 체인 다중 고장 진단 | **1 → 3** | **0.866 → 0.529** | 청구항 5 → 청구항 1·위키 4 |
| 기계 학습 스캔 체인 진단 | 2 → 3 | 0.658 → 0.507 | 위키 4·청구항 1 (같음) |

k = 10에서도 방향은 같다 (문서 수 2→5, 2→3, 2→3 / 겹침 0.68→0.45, 0.63→0.54, 0.63→0.54). 근거 수가 늘면 유사도 검색도 다른 문서를 일부 포함하게 되어 차이가 줄어든다.

## 답변에 미친 영향
스캔 체인 다중 고장 진단 특허, 질문 "이 특허의 핵심 방법은 무엇이고, 스캔 체인은 왜 테스트에 쓰이나?"

| | 유사도 검색 | MMR |
|---|---|---|
| 근거 구성 | 메타데이터 1 + **같은 청구항 문서의 청크 5개** | 메타데이터 1 + 청구항 1 + 위키 '내장 자체시험' 3 + '자동 시험 패턴 생성' 1 |
| 앞 질문(핵심 방법) | 청구항 근거로 정확히 답함 | 같음 |
| 뒷 질문(스캔 체인의 용도) | 근거에 설명이 없는데 메타데이터([근거 1])를 달고 일반론을 씀 | 위키 '내장 자체시험'([근거 3][근거 4])을 근거로 답함 |

유사도 검색은 질문과 가장 가까운 청구항 청크만 모아, 질문 후반부(배경 지식)에 쓸 근거가 빠졌다. 그 결과 LLM이 관련 없는 근거 번호를 붙여 일반론을 쓰는 문제가 생겼다. MMR은 이미 고른 청구항과 비슷한 청크 대신 다른 문서를 골라, 질문의 두 부분을 각각 뒷받침하는 근거를 확보했다.

## 결론과 남은 점
- 복합 질문(특허 내용 + 배경 개념)이 많은 이 서비스에서는 MMR이 근거의 빈자리를 줄이므로 **기본값을 MMR로 바꿨다.**
- 기계 학습 특허처럼 위키 문서(일반 개념, 각 20,000자)가 청구항보다 훨씬 많으면, MMR도 위키 비중을 바꾸지 못했다(위키 4·청구항 1 그대로). 출처 종류별로 근거 수를 나누는 방식은 [f2016_sources.md](f2016_sources.md)의 개선 후보로 남긴다.
- MMR의 '내장 자체시험' 근거는 스캔 체인 자체가 아니라 자체 시험 일반을 설명한다. 다양성이 근거의 정확한 대응까지 보장하지는 않는다.
