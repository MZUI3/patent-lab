# 제품 요구사항 — Patent Lab

## 1. 누구의 어떤 문제인가
**사용자**: 특허를 출원하려는 엔지니어·연구자, 그리고 특정 기술 분야의 특허를 빠르게 파악해야 하는 사람.

**문제**: 선행 특허 조사에서 가장 시간이 드는 일은 비슷한 특허를 찾는 것이 아니라, 찾은 특허의 **청구항을 하나씩 읽으며 "내 아이디어의 어느 구성이 이미 나와 있는가"를 대조하는 것**이다. 청구항은 법률 문장이라 읽기 어렵고, 비슷한 특허가 많아 LLM에 근거 없이 물으면 다른 특허와 섞인 그럴듯한 오답이 나온다 ([RAG 전후 비교](experiments/rag_vs_norag.md): 근거 없는 답은 사실 질문 4개 중 0개 정답).

**이 제품이 하는 일**: 아이디어를 입력하면 가까운 선행 특허를 찾아 **구성요소별로 청구항과 대비하고, 겹친다는 판정마다 청구항 원문 구절을 보여준다.** 특허에 대한 질문은 공보(요약·청구항)와 위키백과에서 찾은 근거만으로 답한다.

**이 제품이 하지 않는 일**: 신규성·진보성·침해 판단. 특허는 법적 판단과 맞닿아 있어 잘못된 답이 사업·법률 판단으로 이어질 수 있으므로, 결과는 "판단 근거를 정리한 것"이고 판단은 변리사 등 전문가 몫이라는 면책 안내를 항상 표시한다.

## 2. 범위와 데이터
| 항목 | 결정 |
|---|---|
| 대상 특허 | 한국 특허. 중심 분야는 반도체 테스트(IPC G01R 31/3183, 전체 985건)이고, 어느 분야 아이디어든 조사할 수 있도록 8개 분야 대표 특허 각 약 1,000건을 미리 두며, 조사할 때마다 KIPRIS 전 분야를 키워드로 검색해 특허를 더한다 (현재 10,284건) |
| 특허 1건의 표현 | 발명의 명칭 · 출원인 · 출원번호 · 출원일 · IPC · 등록 상태 · 요약을 줄 단위로 묶은 색인 텍스트 1개. 요약을 넣어 기술 내용으로 검색되게 한다 |
| 근거 문서 | ① 특허 자체 공보(요약·청구항, KIPRIS 서지 상세) — 항상 수집 ② 기술 개념 설명(한국어 위키백과) — 질문마다 선별 수집 |
| 컬렉션 | `patent_meta`(특허 메타데이터, ID=출원번호) / `patent_docs`(공보·위키 청크, ID=`출원번호:문서ID:순번`, 특허 범위 필터) |

## 3. 기능 요구사항
상태: ✅ 구현·검증 완료. 검증 근거는 [qa.md](qa.md).

| 영역 | 기능 | 요구 | 구현 위치 | 검증 |
|---|---|---|---|---|
| 데이터 | 특허 메타데이터 적재 | 분야별 일괄 수집분과 검색 수집분을 합쳐 로드하고 특허 1건을 색인 텍스트 1개로 만든다 | `data_prep/items.py` | 원본 10,284 → 항목 10,284, 색인 텍스트 7개 속성 |
| 색인 | 메타데이터 색인 | 색인 텍스트를 임베딩해 `patent_meta`에 넣는다. 재실행해도 중복 저장되지 않는다 | `vectorstore/index_meta.py` | 청크 = 항목 수, 재실행 "변경 없음", 색인 검색 상위 10건 = 전수 계산 10/10 |
| 수집 | 검색어 추출 | 특허와 질문에서 위키백과 검색어를 뽑는다. 특허 자체 공보는 항상 수집 대상 | `rag/prompts.py`, `data_prep/collect_docs.py` | 예: `["지터", "반도체 테스트", "신호 품질"]` |
| 수집 | 외부 문서 수집 | 위키 후보를 제목·요약만 보고 선별해 본문을 받는다. 이미 수집한 검색어는 다시 수집하지 않는다 | `data_prep/collect_docs.py`, `kipris.py`, `wiki.py` | 후보 15개 중 1개 색인·14개 버림, 같은 질문 재실행 시 외부 호출 0회 |
| 색인 | 외부 문서 색인 | 청크 크기·중복 설정으로 분할해 `patent_docs`에 넣고 제목·출처·관련 특허를 함께 저장한다 | `vectorstore/index_docs.py` | 1,000/200 → 20청크, 500/100 → 42청크 (같은 문서) |
| 검색 | 근거 검색·병합 | 선택 특허의 메타데이터는 항상 포함하고, 그 특허 범위의 문서 청크를 검색해 병합·중복 제거한다 | `rag/retriever.py` | k=3 → 근거 4개, k=10 → 11개, 다른 특허 문서 혼입 없음 |
| 생성 | 근거 기반 답변 | LangGraph retrieve → generate. 근거만 사용하고, 근거가 없으면 확인되지 않는다고 답한다 | `rag/graph.py`, `rag/prompts.py` | "양산 단가" 질문 → "제공된 문서에서 확인되지 않습니다" |
| 생성 | 근거 표시 | 주장마다 근거 번호를 달고, 실제 인용된 근거만 출처 유형·제목·원문 링크와 표시한다 | `rag/citations.py`, `ui/app.py` | 본문 번호 ↔ 목록 일치, 인용 없음 안내 |
| 화면 | 특허 선택·질의응답 | 조사·탐색 결과나 이름·번호 검색 목록에서 특허를 고르고 특허 패널에서 채팅한다. 대화는 특허별로 분리 | `ui/app.py`, `service/explore.py` | 특허 전환 시 빈 대화, 복귀 시 유지 (AppTest) |
| 핵심 | **선행기술 조사** | 아이디어 → 구성요소 → KIPRIS 키워드 검색으로 대상 확장 → 가까운 특허 최대 5건의 청구항과 구성요소별 대비(개시/일부/미개시). 개시·일부 판정은 청구항 원문 구절을 코드로 확인한 경우만 인정 | `service/prior_art.py`, `data_prep/patent_search.py` | [자동 평가](eval/prior_art_eval.md): Recall@5 85%, 개시율 96% |
| 핵심 | 청구항 해설 | 한 줄 요약·해결 과제·핵심 구성·용어 풀이를 줄마다 근거 번호와 함께 | `service/claim_brief.py` | 3회 실행 모두 12/12줄 인용 |
| 탐색 | 조건 기반 탐색 | "2015년 이후 스캔 체인 고장 진단 등록 특허" 같은 자연어 조건 → 조건을 모두 만족하는 특허 카드 → 특허 패널로 연결 | `service/explore.py` | 연도·상태·출원인 조건 위반 0건 |
| 화면 | 진행 상태·안내 | 단계별 진행 표시, 색인 없음·키 누락 안내, 면책 안내, 오류는 안내만 | `ui/app.py`, `env.py` | AppTest·브라우저 |
| 검색 | MMR 검색 | 질의응답 근거를 다양성 기준으로 고르고 유사도 검색과 비교한다 | `rag/retriever.py`, `eval/compare_search.py` | 출처 문서 수 1→3, 청크 간 겹침 0.866→0.529 → [실험](experiments/mmr_vs_similarity.md) |
| 품질 | RAG 전후 비교 | 대표 질문을 RAG 없이/있이 답하게 하고 사실 정확성·근거 제시·모름 응답으로 비교 | `eval/rag_vs_norag.py` | 사실 정확성 0/4 → 4/4 → [실험](experiments/rag_vs_norag.md) |
| 수집 | 여러 출처 결합 | 공보(XML)와 위키백과(JSON)를 함께 색인하고 근거마다 출처 종류를 표시 | `data_prep/docs.py`, `ui/app.py` | [실험](experiments/multi_source.md) |
| 품질 | 선행기술 조사 자동 평가 | 설정을 바꿀 때 조사 품질을 수치로 비교한다 (Recall@k, 판정 정확도, 비용) | `eval/make_prior_art_cases.py`, `eval/prior_art_eval.py` | [실험 요약표](eval/prior_art_eval.md) |

선택하지 않은 것: 별도 프론트엔드(HTML·CSS·JS). Streamlit으로 화면을 만들고 파이프라인 품질에 시간을 썼다.

## 4. 비기능 요구사항
| 분류 | 요구 | 구현 | 확인 |
|---|---|---|---|
| 성능 | 대표 질문의 처리 시간이 사용에 지장이 없어야 한다 | 문서는 질문 시 필요한 만큼만 수집, 외부 응답 캐시 | 질의응답 4~6초(수집 생략), 처음 질문하는 특허 12~22초 / 선행기술 조사 16초(캐시)~50초(새 키워드) |
| 성능 | 이미 수집·색인한 검색어는 다시 수집하지 않는다 | 특허별 수집 기록 + KIPRIS·위키 응답 파일 캐시 | 같은 질문 재실행 시 외부 호출 0회, 추가 청크 0개 |
| 보안 | 키는 환경변수로 관리하고 소스에 넣지 않는다 | `.env`(git 제외), `.env.example`, 키 읽기는 `src/env.py` 한 곳 | 추적 파일·전체 커밋 이력에서 키 값 0건 |
| 보안 | 화면에 키·프롬프트 전문·오류 추적을 노출하지 않는다 | 화면에는 안내 문구만, 추적은 서버 로그. 오류 메시지의 KIPRIS 키는 `***`로 가림 | 내부 오류 → "처리 중 오류가 발생했습니다"만 표시 |
| 구조 | 수집·색인·검색·생성·UI 책임을 분리하고 도메인 의존 코드는 데이터 준비 영역에 모은다 | `data_prep / vectorstore / rag / service / ui / eval` | KIPRIS·위키 코드는 모두 `data_prep/` |
| 외부 호출 | 재시도·호출 간격을 지키고 출처가 요구하는 식별 정보를 보낸다 | `data_prep/http.py`: 3회 재시도(1·2·4초), 0.5초 간격, 모든 호출 기록. 위키 User-Agent에 연락처. LLM은 분당 요청 상한 | `data/raw/api_calls.log` |
| 비용 | 운영 비용 0원을 유지한다 | LLM은 Gemini 무료 등급(OpenAI 호환), 임베딩은 로컬 bge-m3 | [결정 기록](decisions/005-free-stack.md) |
| 법·윤리 | 데이터·문서의 출처와 이용 조건을 기록하고 지킨다 | 아래 5절, 근거마다 원문 링크 | 위키 근거에 제목·URL (CC BY-SA 출처 표시) |

## 6. 이력
SSAFY AI 코어 프로젝트(2026-10)에서 개인 프로젝트로 시작했다. 과정이 끝난 뒤 무료 스택으로 전환하고([결정 기록](decisions/005-free-stack.md)), 설정 변경을 수치로 비교하는 자동 평가 체계를 더했다([결정 기록](decisions/006-self-retrieval-eval.md)).
