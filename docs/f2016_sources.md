# F2016 여러 종류의 문서 출처 결합

## 출처 종류
| 출처 유형 (`source_type`) | 화면 표시 | 컬렉션 | 수집 방법 | 원문 출처 |
|---|---|---|---|---|
| `item_meta` | 특허 메타데이터 | patent_meta (RAG 1) | KIPRIS Plus 검색 API (XML), 985건 일괄 | KIPRIS 공보 (DOI `10.8080/<출원번호>`) |
| `patent_claims` | KIPRIS 특허공보(청구항) | patent_docs (RAG 2) | KIPRIS Plus 서지 상세 API (XML), 질문한 특허만 | 〃 |
| `wikipedia` | 한국어 위키백과 | patent_docs (RAG 2) | MediaWiki API (JSON) 검색 → 프롬프트2 선별 → 본문 | 위키백과 문서 URL |

세 출처의 유형은 청크 메타데이터 `source_type`에 저장되고 (`src/data_prep/docs.py`의 `SOURCE_LABELS`), 다음 세 곳에서 구분된다.
1. **프롬프트3 근거 블록**: `[근거 n] (출처 유형) 제목` — LLM이 특허 원문과 일반 개념 설명을 구분해 쓴다.
2. **답변 아래 근거 목록**: 근거마다 출처 유형 태그와 원문 링크, 목록 머리에 유형별 개수 (예: `근거 문서 4개 (특허 메타데이터 1 · KIPRIS 특허공보(청구항) 1 · 한국어 위키백과 2)`).
3. **사이드바 색인 현황과 CLI 통계** (`python -m src.vectorstore.index_docs`).

## 출처 종류에 따라 다르게 처리한 것과 이유
| | KIPRIS 청구항 | 위키백과 |
|---|---|---|
| 선별 | **하지 않는다** — 선택한 특허 자체를 다룬 문서는 어떤 규칙보다 우선해 항상 수집 (F2004) | 검색어당 후보 5개를 모아 프롬프트2가 제목·요약만 보고 최대 3개 선별 |
| 길이 규칙 | **적용하지 않는다** — 청구항 일부가 잘리면 권리 범위 설명이 틀어진다 | 200자 미만 제외, 20,000자 초과분은 앞부분만 사용 |
| 텍스트 구성 | `[발명의 명칭]` `[요약]` `[청구항]` 섹션, 청구항 사이 빈 줄, "N. 삭제" 청구항 제외 | API가 준 평문 그대로 |
| 청킹 | 같은 분할기 (1,000자 / 200자 중복). 구분자 우선순위가 빈 줄이라 **청구항 단위로 잘린다** | 같은 분할기. 문단 단위로 잘린다 |
| 청크 제목 머리말 | `[발명의 명칭 (특허공보 번호)]` | `[문서 제목]` |
| 캐시 | 출원번호별 XML | 검색어별 검색 결과, pageid별 본문 JSON |

**청킹을 따로 두지 않은 이유**: 청구항은 이미 "1. …\n\n2. …"처럼 빈 줄로 나뉘어 있어서, 빈 줄을 첫 구분자로 쓰는 공통 분할기가 자연스럽게 청구항 경계에서 자른다. 청구항 1개가 대부분 1,000자보다 짧아 청크 하나에 청구항이 1~3개씩 들어간다 (현재 청구항 청크 평균 816자). 별도 분할기를 두면 설정이 둘로 나뉘어 청크 크기 실험(4.2)이 복잡해지므로 하나로 유지했다.

## 발견한 문제: 출처 간 분량 불균형
기계 학습 특허 하나에서 '인공지능', '딥 러닝', '기계 학습', '지도 학습', '준지도 학습' 같은 일반 문서가 각각 20,000자 상한까지 수집되어 문서당 23~29개 청크가 생겼다. 그 결과 이 특허의 근거 후보는 위키 청크가 청구항 청크(5개)의 20배가 넘고, 유사도·MMR 모두 근거 5개 중 4개를 위키에서 고른다 ([f2014_mmr.md](f2014_mmr.md)).

개선 후보 (아직 적용하지 않음)
- 위키 문서의 길이 상한(`DOC_MAX_CHARS`)을 낮춰 도입부와 앞 절만 쓰기
- 출처 종류별로 근거 수를 나눠 뽑기 (예: 청구항 2 + 위키 3)
- 프롬프트2 선별 기준에 "특허의 기술 분야와 직접 관련된 문서"를 더 강하게 요구하기 (일반 AI 문서 배제)
